# 消息发送设计

日期：2026-10-27  
范围：后端消息发送、管理端配置与发送、登录用户收件箱  
状态：已按讨论确认，等待审阅  

本规格是一次重新设计。实现以本文件为准，不沿用 `docs/superpowers/specs/2026-10-27-message-center-design.md`。

## 1. 目标

一条消息带标题、变量和收件人，发送时按所选渠道各自渲染并投递。收件人可以在系统里看到站内消息。外部系统可以凭渠道 token 往该渠道投一条消息。

第一版渠道类型只有站内、Webhook、Bean。邮件、企微、钉钉以后做成 Bean，不在本版实现。

## 2. 已确认决策

| 项 | 结论 |
|----|------|
| 一条消息和渠道 | 管理端一条消息可选多个渠道。一条消息最多一个站内渠道，Webhook 和 Bean 可以有多个 |
| 站内 | 站内是一种渠道。没选站内渠道就没有收件箱记录 |
| 正文 | 消息上是标题和变量。模板正文放在渠道上，不单独建模板表。一个渠道一份模板，渠道之间不复用 |
| 发送快照 | 发送时把收件人、模板正文、渲染结果、Webhook 地址或 Bean 名称冻在这条消息上。之后改渠道或部门，不影响已发消息 |
| 收件人 | 消息可直接选用户，也可选群组。部门只放在群组里。每个部门带「是否包含下级」。发送时按当时人员展开 |
| 入站 token | 渠道上的 token 给外部系统调用。凭某个渠道的 token 投递时，只走这一个渠道 |
| 第一版投递 | 站内写收件箱。Webhook 每个渠道 POST 一次。Bean 先渲染，再按名称调用 |
| 失败 | 一个渠道失败不影响其他渠道。没有收件人不投递。不自动重试 |
| 草稿 | 没有草稿。管理端点发送即发送 |

## 3. 模块位置

放在 `quickboot-system`，不新建 Maven 模块。

Bean 投递接口放在该模块的 api 包，名称为 `MessageSender`。容器里同名 Bean 必须实现它。入参是一份投递结果：标题、内容类型、渲染后的正文、收件人用户 id 列表。

## 4. 数据模型

用户状态用 `sys_user.status`，字典 `user_status`：`0` 正常，`1` 停用。部门用 `sys_dept` 的 `id` 和 `parent_id`。

### 4.1 渠道 `msg_channel`

| 字段 | 说明 |
|------|------|
| 名称 | 必填 |
| 类型 | `IN_APP`、`WEBHOOK`、`BEAN` |
| 内容类型 | `TEXT`、`HTML`、`JSON`、`MARKDOWN` |
| 模板正文 | 必填。占位符为 `{{name}}`，`name` 由英文字母、数字、下划线组成，括号与名字之间没有空格 |
| 入站 token | 创建时生成 32 字节随机数的十六进制字符串。明文保存，以便管理端再次查看。重置后立即换成新值，旧值失效 |
| Webhook 地址 | 仅 `WEBHOOK` 必填 |
| Bean 名称 | 仅 `BEAN` 必填。保存时容器中必须有这个名字，且类型是 `MessageSender` |
| 状态 | 启用、停用 |

`IN_APP` 不使用地址和 Bean 名称。

### 4.2 群组

`msg_group` 存名称。

`msg_group_user` 存群组与用户 id。

`msg_group_dept` 存群组、部门 id、是否包含下级。保存群组时，部门 id 必须存在。同一个群组里，同一个用户只保留一行，同一个部门只保留一行。群组可以暂时没有用户也没有部门。

### 4.3 消息 `msg_message`

| 字段 | 说明 |
|------|------|
| 标题 | 必填，不能为空白 |
| 变量 | JSON 对象。缺省为 `{}`。字符串原样替换；数字和布尔用字面形式；对象和数组用 JSON 文本。`null` 视为缺少该键 |
| 来源 | `ADMIN` 或 `API` |
| 状态 | `SUCCESS` 全部成功，`PARTIAL` 部分成功，`FAILED` 全部失败 |
| 失败原因 | 只在整次未投递时填写，例如没有收件人、群组不存在 |

直接用户放在 `msg_message_user`。所选群组放在 `msg_message_group`。

### 4.4 渠道快照 `msg_message_channel`

每个所选渠道一行，包括未投递成功的渠道。渠道 id 记录请求中的 id，不因渠道后来被删除而级联删除快照。

| 字段 | 说明 |
|------|------|
| 渠道 id | 指向发送当时的渠道 |
| 内容类型 | 抄自渠道 |
| 模板正文 | 抄自渠道 |
| 渲染正文 | 渲染成功才有 |
| Webhook 地址 | Webhook 渠道抄一份 |
| Bean 名称 | Bean 渠道抄一份 |
| 投递状态 | `SUCCESS` 或 `FAILED` |
| 错误信息 | 失败时填写，最长 500 字 |

### 4.5 收件人快照 `msg_message_recipient`

解析完成后的用户 id，同一条消息里每个用户一行。没有收件人时不写这张表。

### 4.6 收件箱 `msg_inbox`

只有站内渠道渲染并投递成功时才写。每个收件人一行，含 `read_at`。未读时 `read_at` 为空。同一条消息、同一个用户只有一行。

## 5. 发送流程

管理端和外部调用进入同一条发送流程。外部投递不使用登录会话，只校验 token。管理端发送需要登录，并具备 `message:message:send`。

外部接口为 `POST message/open/send`。请求头 `X-Message-Token`。成功和业务失败（没有收件人、群组不存在、部分渠道失败）都返回消息 id、消息状态，以及已产生的渠道投递状态。token 错误或渠道停用时返回错误，没有消息 id。

管理端发送为 `POST message/message/send`。收件箱列表为 `POST message/inbox/page`，详情为 `GET message/inbox/{id}`，详情接口负责标已读。

1. 管理端未选渠道：拒绝，不产生消息。外部调用的渠道来自 token，不在请求里再选。
2. 外部 token 对不上，或该渠道已停用：拒绝，不产生消息。
3. 请求里的群组 id 有不存在的：产生一条消息，状态 `FAILED`，写明原因。仍保存标题、变量、直接用户和请求中的群组 id。不展开收件人，不写渠道快照，不投递。
4. 展开收件人：
   - 直接用户、群组中的用户：用户必须存在且状态为正常，否则忽略。
   - 部门未勾选包含下级：只取 `dept_id` 等于该部门、且状态为正常的用户。
   - 部门勾选包含下级：加上沿 `parent_id` 能到达的全部下级部门中的正常用户。部门 id 重复出现时停止，避免环。
   - 部门已删除：该部门贡献零个用户，不因此失败整次发送。
   - 部门是否停用：不影响展开。
   - 按用户 id 去重。顺序不作为验收条件。
5. 展开后没有人：消息状态 `FAILED`，失败原因为「没有收件人」。不写收件人快照，不写渠道快照，不写收件箱，不 POST，不调用 Bean。
6. 有收件人时，对每个所选渠道各做一次，互不影响：
   - 渠道不存在：仍写一行快照，渠道 id 为请求中的 id，模板正文为空，状态 `FAILED`，不投递。渠道已停用：抄下当时仍能读到的模板和地址或 Bean 名称，状态 `FAILED`，不投递。
   - 模板按 `{{name}}` 替换。缺少某个键：该渠道 `FAILED`，不投递。
   - 站内渲染成功：为每个收件人写一行未读收件箱，该渠道 `SUCCESS`。
   - Webhook：向快照里的地址 POST 一次，`Content-Type` 为 `application/json`，超时 10 秒。HTTP 2xx 为成功。超时、网络错误、其他状态码为失败，并记下原因。
   - Bean：按快照里的名称从容器取出 `MessageSender` 并调用。名称不存在、类型不对或抛出异常：该渠道 `FAILED`，原因取异常信息并截到 500 字。
7. 全部渠道 `SUCCESS` 则消息为 `SUCCESS`。有成功也有失败则为 `PARTIAL`。全部 `FAILED` 则为 `FAILED`。全部渠道失败时，消息上的失败原因为空，原因写在各渠道快照上。

Webhook 和 Bean 收到的 JSON 字段相同：

| 字段 | 含义 |
|------|------|
| title | 消息标题 |
| contentType | `TEXT`、`HTML`、`JSON`、`MARKDOWN` |
| content | 该渠道渲染后的正文 |
| recipientUserIds | 本次冻结的收件人用户 id |

出站请求不携带入站 token。

## 6. 三条入口

### 6.1 管理端

三个管理页：渠道、群组、发送记录。发送记录页可以发起发送。

创建渠道时生成 token。渠道详情可以查看 token，并可以重置。

群组维护用户，以及部门加「是否包含下级」。

发送时填写标题、变量、直接用户、群组、渠道。点发送即按第 5 节执行。

权限码：

| 权限 | 能力 |
|------|------|
| `message:channel:list` / `query` / `add` / `edit` / `remove` | 渠道维护 |
| `message:channel:resetToken` | 重置 token |
| `message:group:list` / `query` / `add` / `edit` / `remove` | 群组维护 |
| `message:message:list` / `query` / `send` | 查看发送记录、发起发送 |

### 6.2 外部调用

请求头 `X-Message-Token` 为渠道 token。正文为标题、变量、用户 id 列表、群组 id 列表。用户和群组都可以空，空则按「没有收件人」产生失败消息。

不能在请求里指定其他渠道。

日志不记录 token。

### 6.3 收件箱

登录用户即可查看，不另设按钮权限。只能看到自己的行。按消息创建时间倒序。

列表展示标题和未读状态。打开详情返回站内渠道那份渲染正文和内容类型，并把 `read_at` 写成当前时间。列表本身不改为已读。

展示：`TEXT` 按纯文本，`HTML` 按 HTML，`MARKDOWN` 按 Markdown，`JSON` 按格式化文本，不执行。

用别人的收件箱 id 查询，按不存在处理。

后来加入部门的人不会补进已发消息。

## 7. 验收

收件人：

- 直接用户、群组用户、部门用户合并后，同一个人只有一行快照、一行收件箱。
- 包含下级为真时含下级部门的正常用户；为假时只含该部门直接所属的正常用户。
- 停用用户不进入收件人。
- 展开后没有人：消息 `FAILED`，原因为「没有收件人」，没有收件箱，没有 Webhook 调用，没有 Bean 调用。
- 发送后部门新增用户，已发消息的收件人快照不变。

模板和投递：

- 不存在独立模板表。模板正文在渠道上。
- 发送后修改渠道模板、Webhook 地址或 Bean 名称，已发消息的快照和收件箱正文不变。
- 某个渠道缺少 `{{name}}` 对应的变量，只该渠道 `FAILED`，其他渠道仍投递。
- 选了站内：每个收件人一行，初始未读，打开详情后已读。没选站内：没有收件箱。
- 每个 Webhook 渠道只 POST 一次。Bean 使用发送当时抄下的名称。两者收到标题、内容类型、渲染正文、收件人。
- 一个渠道失败时消息为 `PARTIAL`。全部成功为 `SUCCESS`。全部失败为 `FAILED`。失败后不自动再次投递。

入口：

- 外部 token 只投所属渠道。
- token 错误或渠道停用：不产生消息。
- 管理端可选多个渠道，其中站内最多一个。
- 管理端选了停用渠道：该渠道失败，其他渠道继续。
- 重置 token 后，旧 token 不能再投消息。

## 8. 不在本版

- 邮件、企微、钉钉、短信的内置渠道
- 自动重试、草稿、再次发送
- 按收件人拆成多次 Webhook
- 可复用的模板库
- 外部渠道的已读回执
